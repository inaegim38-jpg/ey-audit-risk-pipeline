# 포렌식 케이스 워크벤치

거래 데이터 검증 파이프라인 위에 **증거·문서·조사** 계층을 얹은 확장입니다. 기존 `audit_risk` 스키마는 "거래가 규칙에 맞는가"를 봤다면, `forensic` 계층은 "이 케이스에서 무엇을 확보했고, 무엇을 읽었고, 무엇이 남았는가"를 남깁니다.

## 1. 왜 이 계층이 필요한가

기존 프로젝트는 8277건의 탐지 결과를 냈지만, 구조적으로 세 가지가 비어 있었습니다.

첫째, **문서가 없었습니다.** 모든 입력이 정형 거래였고, 실제 조사에서 가장 많은 시간을 쓰는 문서 검토(이메일·품의서·견적서·계산서)가 빠져 있었습니다.

둘째, **증거 개념이 없었습니다.** `evidence_doc_no` 는 문자열 컬럼일 뿐, 파일·해시·수집 이력이 없었습니다. 법정 제출이나 규제 대응을 염두에 둔 조사라면 "이 파일이 언제 누구에 의해 어떤 매체에서 확보되었고, 이후 바뀌지 않았다"는 사실을 보여줄 수 있어야 합니다.

셋째, **조사 서사가 없었습니다.** "룰별 탐지 건수"는 분석 결과지만, 조사 보고서는 "무엇이 문제이고, 근거가 무엇이며, 무엇이 아직 확인되지 않았는가"를 파인딩 단위로 정리해야 합니다.

이 계층은 그 셋을 채웁니다. 기존 엔진은 없애지 않고, 데이터 분석 모듈로 그대로 남겨 두었습니다.

## 2. 케이스 설계

실제 기업 자료를 쓸 수 없으므로, 탐지 절차를 검증할 수 있는 가상 케이스를 생성합니다.

| 항목 | 내용 |
|---|---|
| 케이스 | CASE-2026-014, 한빛물산(주) 구매팀 법인카드·협력사 지급 제보 |
| 기간 | 2025-09-01 ~ 2026-06-30 |
| 문서 | 563건 (메일 311, 품의서 64, 견적서 83, 계산서 84, 회의록 20, 카드내역 1) + 카드 승인 206건 |
| 생성 | `python3 -m forensic.run_demo` (시드 고정, 재현 가능) |

주입한 패턴은 여섯 가지입니다. 생성기는 `ground_truth.json` 에 정답을 남기지만, **탐지 단계는 이 파일을 읽지 않습니다.** 정답을 보고 맞히는 구조가 아니라는 점을 코드로 보장합니다.

| 패턴 | 주입 내용 | 탐지 파인딩 |
|---|---|---|
| 분할 발주 | 한도 1,000만원 직하 4건, 9일 내, 동일 업체 | F-002 |
| 허위 비교견적 | 3개 업체 견적 금액·연락처 동일 | F-008 |
| 특수관계자 | 세영산업이 대성기업과 주소·연락처 공유 | F-003 |
| 중복 지급 | 동일 승인번호 계산서 2개 일자 | F-001 |
| 일자 조작 | 계약일자가 계산서 작성일자보다 늦음 | F-004 |
| 카드 사적 사용 | 주말·심야 골프장·유흥주점 6건 | F-005 |

여기에 정답이 없는 참고 지표 두 개(벤포드 편차, 결재 집중)를 더해 8건의 파인딩이 나옵니다. 주입 패턴 6개가 모두 탐지되었고, 오탐은 참고 지표 2건입니다.

## 3. 파이프라인

```
[코퍼스 생성] → [증거 수집·해시] → [문서 검토] → [교차 분석] → [보고서]
     합성            manifest          index/tag      findings      인용·한계
                     custody_log       review queue   evidence link
```

각 단계는 다음 단계가 신뢰할 수 있는 산출물을 남깁니다.

**증거 수집(`intake.py`)** 은 파일을 읽기 전용으로 복사하고 SHA-256을 계산합니다. `evidence_manifest.csv` 에 파일 1건당 1행, `custody_log.csv` 에 수집·해시검증 이벤트를 남깁니다. 수집 후 `verify()` 로 재해시해 원본 변경·누락·미등록 파일을 확인합니다. 데모에서는 563건 전부 `PASS` 입니다.

**문서 검토(`review.py`)** 는 파일을 정규화 텍스트와 메타데이터로 바꾸고, 중복을 정리하고, 스레드를 재구성하고, 규칙 기반으로 사전 태깅합니다. 산출물은 검토 큐 엑셀입니다.

**교차 분석(`analytics.py`)** 은 문서 1건으로는 알 수 없는 패턴을 찾습니다. 중복 지급, 분할 발주, 업체 마스터 이상, 일자 역전, 카드 이상, 벤포드, 결재 집중, 라운드 금액, 동일 견적의 9개 규칙입니다.

**보고서(`report.py`)** 는 파인딩마다 증거 ID·파일 경로·해시 앞 12자리를 붙여 인용합니다. 같은 결론에 제3자가 도달할 수 있는지 검증할 수 있게 하려는 것입니다.

## 4. 중복 판정을 문서 유형별로 나눈 이유

처음에는 모든 문서에 본문 유사도(5-문자 shingle의 Jaccard)를 적용했습니다. 결과가 틀렸습니다. 품의서·견적서·계산서는 본문이 템플릿이라 서로 다른 문서도 유사도가 0.9를 넘었고, 563건 중 559건이 26개 클러스터로 뭉쳤습니다. 이 상태의 "근접중복 99%"는 아무 의미가 없습니다.

그래서 판정 기준을 나눴습니다.

| 유형 | 판정 기준 | 이유 |
|---|---|---|
| 메일 | 본문 shingle Jaccard ≥ 0.90 (MinHash + LSH로 후보 축소) | 본문이 자유 서술이라 텍스트 유사도가 의미를 가짐 |
| 계산서 | 승인번호 일치 | 같은 승인번호는 같은 계산서 |
| 견적서 | 합계금액 + 담당자 연락처 일치 | 독립 견적이 이 조합까지 같기 어려움 |
| 품의서 | 협력사 + 금액 + 품명 일치 | 반복 용역의 우연 일치를 배제 |

이렇게 바꾼 뒤 클러스터는 42개로 줄었고, 그중 의미 있는 것은 3개 업체 동일 견적(F-008)과 동일 승인번호 계산서(F-001)입니다.

## 5. 검토 큐 우선순위

자동 태깅의 목적은 판단이 아니라 **볼 순서**를 정하는 것입니다. 우선순위는 다음 합입니다.

```
priority = Σ(태그 가중치) + 문서유형 가중치 + 근접중복 가중(1.0) + 동일문서 가중(1.5)
```

태그 가중치는 정황의 강도에 따라 5(분할·견적통제), 4(은폐·특수관계·중복지급), 3(사적카드), 2(한도근접), 1(PII)로 두었습니다. 여기에 교차 분석에서 파인딩과 연결된 문서는 +3을 더합니다. 문서 1건만 봐서는 알 수 없던 사실이 파인딩으로 확정되면, 그 문서를 다시 볼 이유가 생기기 때문입니다.

결과적으로 상위 15건이 HIGH로 올라오고, 그 안에 분할 발주 4건·동일 견적 3건·중복 지급 2건이 모두 들어옵니다.

## 6. QC 지표

검토 품질을 주장하려면 숫자가 있어야 합니다. 데모에서 측정하는 값은 네 개입니다.

| 지표 | 값 | 의미 |
|---|---|---|
| 태그 커버리지 | 29.5% | 위험 태그가 붙은 문서 비율. 나머지는 정상 문서라는 뜻이며, 낮다고 실패가 아님 |
| 클러스터 내 제안 일관성 | 92.9% | 같은 근접중복 클러스터의 문서가 같은 관련성 제안을 받았는지 |
| PII 포함 문서 | 83건 | 마스킹 대상. 검토 콘솔 본문 발췌에서 주민번호·계좌번호를 마스킹 |
| 파인딩 증거 연결 | 20건 | 파인딩 8건에 연결된 증거 파일 수 (F-006은 모집단 통계라 인용 없음) |

클러스터 일관성이 100%가 아닌 것은, 같은 클러스터라도 한 문서에만 추가 태그가 붙어 제안 등급이 갈리기 때문입니다. 이 경우 상위 등급으로 검토하도록 두었습니다.

## 7. 한계

가장 중요한 한계는 **이 케이스가 합성이라는 점**입니다. 탐지 규칙이 의도한 패턴을 잡는지는 확인할 수 있지만, 실제 데이터의 노이즈·예외·누락을 견디는지는 검증하지 못했습니다. 보고서에도 이 문장을 그대로 넣었습니다.

두 번째는 **표본 크기**입니다. 계산서 84건으로 벤포드를 적용하면 MAD가 0.0498로 나오는데, Nigrini 기준(0.015)을 넘지만 표본이 작아 단독 근거가 될 수 없습니다. 그래서 심각도를 MEDIUM으로 낮추고 "참고 지표"로 표기했습니다.

세 번째는 **지급 이력 부재**입니다. 중복 지급(F-001)은 계산서가 두 번 존재한다는 사실만 보여줍니다. 실제 이체 내역이 없으면 지급이 두 번 이루어졌는지는 확정할 수 없습니다. 이 한계를 파인딩마다 명시했습니다.

네 번째는 **권한·보존 정책의 미구현**입니다. 스키마에는 `legal_hold` 와 접근 이력 필드가 있지만, 실제 접근 통제와 파기 정책은 구현하지 않았습니다. 실무에서 이 부분은 IT·법무와 함께 설계해야 합니다.

## 8. 다음 단계
