# 포트폴리오 재구성 V3 — 감사·리스크 자료 정합성 및 검토 이슈 트래커

## 한 줄 정의
거래·증빙 자료를 접수·정규화하고, 정합성(DQ)·증빙·이상 후보를 규칙으로 뽑아, **사람이 검토하고 보완 요청 상태를 추적**할 수 있게 정리하는 자료 정리·검토 지원 파이프라인. 규칙은 후보를 제시할 뿐 부정 여부를 판단하지 않습니다.

## 공고 직무와의 대응
| 공고 담당업무 | 이 프로젝트에서 한 일 | 위치 |
|---|---|---|
| 자료 정리·데이터 관리 지원 | 수신 파일 manifest 검증(해시·행수), 거래·증빙 정규화 적재, 멱등 upsert | `n8n/wfA_portfolio_intake.json`, `sql/27` |
| 문서 검토·산출물 정리 지원 | 증빙 누락·금액·일자 불일치, 중복 문서 후보, 검토 큐와 보완 요청 제안 | `portfolio.run_checks`, `review_item`, `issue_log` |
| 조사·분석 지원 | 분할 결제·업무 외 시간·근접 반복 후보, 우선순위 점수 | AN_02~04, `priority_score` |
| 기타 지원 | Power BI용 요약·검토 큐 뷰 | `vw_pbi_*`, `powerbi/PORTFOLIO_DASHBOARD_SPEC.md` |

## 흐름
자료 접수(WF-A) → 정규화·적재 → `run_checks`(DQ/증빙/이상 후보, WF-B) → 검토 항목·보완 요청 **제안** 생성 → 사람이 `set_review_status`로 판정 → 현황 조회(WF-C) → Power BI.

## 고정 자동화 계층과의 경계
이 저장소의 자동화 계약은 [Architecture v2](ARCHITECTURE_V2.md) §2의 **WF-1~WF-5**이며, 이번 작업은 해당 workflow JSON을 수정하지 않습니다. 아래 WF-A~WF-C는 포트폴리오 시연을 위해 **별도로** 둔 산출물로, 운영 계약에 연결하지 않았고 모두 `active=false`입니다. 따라서 WF-A~WF-C는 WF-2(PBC tie-out)나 WF-3(룰 엔진)를 대체하지 않으며, 동일한 `portfolio` 스키마와 `run_checks()`를 호출하는 독립 실행 경로로만 존재합니다.

## 설계 결정과 이유
- **임계값은 `rule_param` 테이블**: 코드 수정 없이 조정하고, 값이 없으면 기본값으로 때우지 않고 실패(fail-closed).
- **멱등 실행**: 같은 입력으로 `run_checks`를 다시 돌려도 후보가 늘지 않고, 검토자가 바꾼 상태는 덮어쓰지 않습니다.
- **중복 문서는 거부하지 않고 표시**: 같은 해시의 두 번째 문서는 `duplicate_of`에 원본을 기록해 DQ_03 후보로 남깁니다. 거부하면 "중복이 들어왔다"는 기록이 사라집니다. `duplicate_of`는 트리거가 계산하므로 입력값을 위조할 수 없고, 원본은 부분 유니크 인덱스로 하나만 허용됩니다.
- **사람이 판정**: 워크플로우는 `review_status`를 바꾸지 않습니다. 변경 경로는 `set_review_status` 하나이며 reviewer가 필요합니다.
- **외부 발송 없음**: 이슈는 `PROPOSED`(제안) 상태로만 생성됩니다. 메일·Slack 노드는 포함하지 않았습니다.

## 한계 (면접에서 먼저 말할 것)
- 데이터는 전부 합성이며 거래 10건 규모입니다. 규모·성능에 대한 주장은 하지 않습니다.
- 룰 임계값(50만 원, 100만 원 등)은 데모용 가정이며 실제 기준이 아닙니다.
- 탐지 결과는 "룰이 의도대로 동작하는지" 확인용이고 정확도·재현율 지표가 아닙니다. 픽스처가 룰에 맞춰 설계되었습니다.
- Power BI `.pbix`는 만들지 않았고, 클라우드 갱신·Slack·메일은 연결하지 않았습니다.
- 코드는 AI(Claude) 도움을 받아 작성했고, 작성자가 실행 결과를 확인하며 검토했습니다.
