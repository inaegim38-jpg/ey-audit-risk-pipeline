## 1. 목적과 범위

**목적**: 거래 데이터에 대해 (가) 데이터 품질(결측·0원 이하·중복), (나) 증빙 대사(누락·금액 불일치·일자 괴리), (다) 이상 징후(통계적 이상치·분할결제·업무 외 시간·근접 반복)를 SQL 룰로 일괄 점검하고, 결과를 검토 목록(Excel)과 대시보드로 넘기는 절차를 재현 가능하게 구현한다.

**범위와 트랙 구분**

| 트랙 | source_dataset | 거래 건수 | 성격 | 적용 룰 |
|---|---|---:|---|---|
| A | `BANKSIM_REAL` | 20000 | 공개 **시뮬레이션** 은행 거래 + **합성 증빙**(결함을 기능 검증용으로 주입) | DQ, EV, AN 전체 |
| B | `SEOUL_OA22156` | 178762 | **실제 공개 지출** 데이터, **증빙 없음** | DQ, AN (EV_01~03 제외) |

**범위 밖**: 실제 기업 원장, 실제 증빙 원본, 담당자 소명, 법규 위반 여부 판단.

## 2. 데이터 출처, 프로파일링, 정제 전후와 한계

### 2.1 출처
- **BankSim**: Kaggle `ealaxi/banksim1`(공개 시뮬레이션 데이터)에서 무작위 표본 20,000건(시드 고정). 시각(원본은 일 단위 step → 12:00 고정), 금액(환율 1,400원 가정), 부서(고객 연령대 코드 대체)는 가정으로 채움. 증빙 19,983건은 거래에서 파생한 **합성** 데이터.
- **서울시**: 서울 열린데이터광장 「서울시 본청 업무추진비 목록」(OA-22156) CSV(cp949). 원본 파일 68,492,687바이트 → 정규화 CSV(`data/seoul_normalized.csv`) 41,865,357바이트 → `raw_transactions`에 178,762건 적재. 두 파일 모두 Git 제외.

### 2.3 정제 내용 (서울시, `python/load_seoul_expense.py`)
- 열 매핑: 부서명→`department_code`/`account_id`, 집행장소→`merchant_id`, 비목→`merchant_category`(`SEOUL_` 접두), 문서고유id→`evidence_doc_no`, 결제방법 '현금'→`tx_type=CASH`.
- **시각 플레이스홀더 분리**: 집행일시가 `00:00`인 행은 실제 심야 집행이 아니라 시각 미입력으로 보고 `has_exact_time=false`로 분리 → **1562건**(나머지 177200건은 `true`). AN_03은 `has_exact_time=false` 건에 대해 심야 판정을 하지 않고 주말 판정만 적용.

### 2.4 한계
- **1970-01-01 60건**: 원본 값 자체인지 파싱 결과인지 원본 대조를 하지 않았음(미확인). AN_01 1건이 이 중에 포함됨.
- 서울시 데이터에는 증빙이 없으므로 EV 룰을 적용할 수 없음.
- BankSim의 시각·금액·부서는 가정값이므로 AN_03, AN_04 결과는 실제 업무 패턴을 의미하지 않음.
- 정규화 단계에서 적재 행 수(178,762) 외의 필드 단위 원본 대사는 수행하지 않음.

## 5. 해석상 주의와 한계

1. **어떤 결과도 '부정 적발'이 아니다.** BankSim은 시뮬레이션이고, 그 증빙은 합성이며 EV_01~03·DQ_03(BankSim)의 건수는 기능 검증을 위해 **의도적으로 주입한 결함**을 반영한 값이다. 탐지 성능(정확도·재현율) 지표가 아니다.
2. **서울시 데이터는 실제 공개 지출이지만 증빙·내부 규정·소명이 없다.** 탐지 건은 '추가 확인이 필요할 수 있는 후보'일 뿐이며, 예컨대 AN_02 14건은 한도 직하 금액이 같은 날 같은 곳에서 반복된 패턴일 뿐 분할결제 의도를 입증하지 않는다. 100만 원 한도 자체가 프로젝트 가정이다.
3. **threshold_value는 근거 있는 법적 기준이 아닌 가정값**이며, 값을 바꾸면 건수가 달라진다(민감도 쿼리: `sql/05_seoul_analysis.sql`).
4. AN_01 서울시 2712건은 SEOUL_기관 카테고리처럼 표준편차가 평균보다 큰 치우친 분포에 Z-Score를 적용한 결과로, 고액 집행이 많이 걸리는 구조적 한계가 있다.
5. AN_04는 동일 금액의 정기 집행도 걸리므로 오탐 비중이 높을 수 있다. BankSim의 AN_04 1547건은 부서가 연령대 코드인 가정 데이터에서 나온 값이다.
6. 서울시 DQ_03 707건은 동일 계정·장소·금액·시각 행이 원본에 여러 번 있는 경우로, 원본 중복 게시인지 실제 복수 집행인지 확인하지 않았다.
7. 1970-01-01 일자 60건은 원본 확인 전까지 정제 한계로 남는다.
8. **이슈 상태 3건(IN_REVIEW 1, RESOLVED 1, FALSE_POSITIVE 1)은 `sql/04_demo_review.sql`의 시연용 변경이며 실제 검토 결과가 아니다.** 나머지 8274건은 OPEN.
